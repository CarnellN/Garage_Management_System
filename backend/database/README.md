# Database integration handoff

The database developer owns schema creation, migrations, indexes, grants and seed data. The Express server does not create or alter tables. This document states the server's expected interface, based on the originally shared schema and the extensions already identified in [the OpenAPI contract](../../docs/openapi.yaml).

The server uses uppercase table names and lowercase column names, quoted per engine: `CUSTOMER`, `VEHICLE`, `BOOKING`, `USER`, `JOB_CARD`, `TASK`, `PART`, `JOB_PARTS`, `INVOICE`, `PAYMENT`. Preserve the original primary/foreign keys, uniqueness and numeric constraints. IDs are positive signed INTs with database-generated identity/auto-increment for entity IDs. On PostgreSQL, quoted uppercase names are case-sensitive. If the actual schema uses a different naming convention, coordinate the mapping before integration; do not silently duplicate tables.

Use MySQL 8.0.16+ with InnoDB by default. Supabase/PostgreSQL remains a selectable alternative. Use UTC storage: MySQL DATETIME(3) and PostgreSQL TIMESTAMPTZ for all timestamps. MySQL connections format JS dates in UTC; PostgreSQL timestamp-with-time-zone decoding returns dates. The API returns RFC 3339 UTC timestamps. Monetary columns must stay exact DECIMAL/NUMERIC; drivers return these as strings.

## Additional columns on shared tables

| Table | Server-required additions |
| --- | --- |
| USER | `email VARCHAR(160)` unique normalized lowercase login, `password_hash VARCHAR(255)`, `active BOOLEAN NOT NULL`, `customer_id INT NULL UNIQUE` FK to CUSTOMER. CUSTOMER role requires a customer link; staff roles require null. Role must be one of CUSTOMER/RECEPTIONIST/MECHANIC/ADMIN. |
| BOOKING | `ends_at` timestamp, `bay_id` FK to BAY, `version INT NOT NULL` starting at 1, non-null status. |
| JOB_CARD | `version INT NOT NULL` starting at 1, non-null status; unique non-null `booking_id`. |
| JOB_PARTS | `unit_price_snapshot DECIMAL(10,2) NOT NULL`, captured on first use. |
| PAYMENT | `transaction_reference VARCHAR(120) NULL UNIQUE` globally across verified non-cash payments; `method` non-null for new records. Multiple cash rows have null references. |

Password hashes are generated by the server using salted scrypt, stored as `scrypt$32768$8$1$<32 hex salt>$<128 hex hash>`. Never store plaintext passwords. Existing accounts with a different hash scheme require an explicit migration/verification strategy; the server does not silently accept another format. The first active ADMIN is provisioned out of band by the database/deployment owner using a server-generated hash and a null customer link. Server staff provisioning requires that initial authenticated admin.

## Supporting tables expected by the server

These are interface requirements for coordination, not executable DDL.

| Table | Columns and constraints |
| --- | --- |
| AUTH_SESSION | `session_id CHAR(36)` PK UUID, `user_id INT` FK USER, `created_at`, `expires_at` non-null UTC timestamps, `revoked_at` nullable UTC timestamp. Index user_id and expiry for revocation/cleanup. |
| BAY | `bay_id INT` PK, `enabled BOOLEAN NOT NULL`. Seed at least one enabled bay before scheduling. The server reads/locks this catalog; bay administration is out of band. |
| SERVICE_TASK | `service_task_id INT` generated PK, `name VARCHAR(120)` required, `standard_hours DECIMAL(6,2)` nullable nonnegative. Separate from TASK, whose job_card_id remains required. |
| INVOICE_LINE | `line_id INT` generated PK, `invoice_id INT` FK INVOICE, `kind VARCHAR(10)` LABOR/PART, `description VARCHAR(120)`, `quantity DECIMAL(12,2)`, `unit_price DECIMAL(10,2)`, `line_total DECIMAL(12,2)`, all required and nonnegative. Immutable after issuance. |
| AUDIT_EVENT | `audit_id INT` generated PK, `actor_user_id INT NULL` FK USER, `action VARCHAR(100)`, `resource_type VARCHAR(60)`, `resource_id VARCHAR(80) NULL`, `occurred_at` UTC timestamp, `request_id VARCHAR(100)`, `outcome VARCHAR(10)` SUCCESS/DENIED/FAILURE. All except actor/resource ID required. Index time/ID and resource lookup. Append-only through the application. |
| IDEMPOTENCY_KEY | `user_id INT` FK USER, `method VARCHAR(10)`, `path VARCHAR(255)`, `key VARCHAR(128)`, unique together as `(user_id, method, path, key)`; `request_hash CHAR(64)`, `response_json` JSON/text, `created_at`, `expires_at` UTC timestamps. Required fields. Store response as JSON and retain at least 24 hours. Index expiry. Use case-sensitive comparisons for method/path/key; do not use a case-insensitive MySQL collation for retry keys. |

No PAYMENT_INTENT storage is consumed yet: the two checkout operations return PAYMENT_PROVIDER_NOT_CONFIGURED until a real provider is integrated. Introduce pending-balance reservations, authenticated callbacks, transaction deduplication and reconciliation together before enabling online payments. The current payment endpoint is staff-only recording of completed transactions.

## Transaction and constraint expectations

Successful mutations, audit events and retry responses commit in one transaction. Missing supporting tables cause rollback and `503 SCHEMA_NOT_READY`; the server will not perform unaudited writes or bypass durable retry handling. Runtime database grants must permit the documented reads and mutations, including SELECT FOR UPDATE, while restricting schema changes. Restrict direct audit/invoice/payment edits and use separate migration credentials.

Booking reservation locks the vehicle, then all enabled BAY rows in ascending ID order, then reads conflicting active bookings with FOR UPDATE before selecting capacity. This conservative strategy serializes reservations across the garage and works on both engines when every writer follows the protocol. External booking writers must follow the same locks or use equivalent database-enforced overlap protection. PENDING/CONFIRMED/CHECKED_IN occupy half-open intervals; adjacent bookings may share an endpoint. Index booking vehicle/time and bay/time, and require ends_at > scheduled_at. Do not disable/delete bays while active reservations refer to them.

Job writes lock the parent job, enforce the ETag version and increment it for task/part edits. Job creation locks the vehicle and checks for an existing nonterminal job. Preserve a unique non-null booking relationship. Invoices require unique job_card_id. Payments lock the invoice and use current locking payment reads before checking balance; unique provider references and retry-key uniqueness protect duplicates. Deadlocks/serialization conflicts roll back and return 409; mutations are not automatically retried. Test overlapping booking requests, competing invoice creation, duplicate payments and overpayments on both real engines before release.

Foreign keys should restrict deletion of service/financial history; do not cascade-delete invoices, payments, job cards or bookings. The vehicle deletion endpoint only deletes unused vehicles, and catalog part deletion rejects referenced usage. Preserve nullable original contact/make/model/standard-hour/catalog-price fields. Backfill legacy role/status values before serving endpoints, and ensure all CASE/uniqueness rules match server normalization.

No live engine or schema integration has been verified by the mocked HTTP tests. Once provisioned, configure `backend/server/.env`, run `npm run db:check`, and run the frontend flows against the actual schema. Confirm constraints, collation, identity behavior, timestamp serialization and concurrency separately from connectivity.
